# VPS rehearsal — 2026-09-04

Status: Partial Task 7 acceptance evidence

This drill exercised the self-hosted install, upgrade, rollback, backup,
restore and application-build paths on a fresh temporary VPS. It found three
release-path defects and one retry race that fake-command tests had not exposed.
All four were corrected; install and deploy were repeated successfully, while
the retry invariants also received focused unit and race-detector coverage.

It is deliberately **not** the final Task 7 acceptance record. The repository
had no published SemVer tag and no public release image, the supplied host had
4 GB rather than 1 GB of RAM, and the backup was local and unencrypted.

GHCR availability or the GitHub release workflow.

That was useful for checking the insecure-evaluation branch of the installer;
it is not an acceptable production edge.

## Results

- A clean `snaphostctl install v0.0.5` completed after the defects below were
  fixed. Checkout, protected env and current state all named the same tag;
  the env was mode `0600`, state and backup directories were `0700`, the
  AppArmor profile parsed, both containers became healthy, and the backup
  timer was enabled.
- `/health` and the embedded panel returned 200, an anonymous protected API
  call returned 401, and operator login plus an authenticated project listing
  returned 200.
- The scheduled backup produced a 10,774-byte SQLite dump and checksum, both
  mode `0600`. `backup.sh verify` accepted it. Restoring it into a throwaway
  database returned `PRAGMA integrity_check = ok`, retained the operator row
  and exposed all expected tables. The live volume was not changed.
- No-argument upgrade selected `v0.0.6`. Checkout, env and state moved
  together and the login session survived. Rollback dry-run correctly refused
  a release whose migrations were not declared backward compatible; the
  explicit compatibility override made dry-run and real rollback succeed.
  The runtime, checkout and state returned to `v0.0.5` and remained healthy.
- The corrected release upgraded from `v0.0.5` to `v0.0.7` in 26 seconds.
  Compose created the host-visible `snaphost-net`, checkout/env/state agreed,
  and both platform containers were healthy.
- A standard React/Vite archive then built and ran successfully. The generated
  container joined its isolated per-deploy network and `snaphost-net`, and its
  rendered HTML and JavaScript were fetched directly from the container.

## Build-pressure measurement

Before the measured cold build, `buildctl prune --all` reclaimed 1.31 GB and
reported zero remaining cache. The already deployed Vite site stayed running.
A modified Vite archive was then built as a second deploy while memory was
sampled from `/proc/meminfo` once per second.

| Measurement | Result |
| --- | --- |
| Build duration | 147 seconds |
| Samples | 189 |
| Peak `MemTotal - MemAvailable` | 997.2 MiB |
| Minimum `MemAvailable` | 2,916.6 MiB |
| Maximum swap used | 0 MiB |
| Kernel OOM events | 0 |
| Control-plane restarts | 0 |
| BuildKit restarts | 0 |
| First site during and after build | running and serving |
| New site after build | running and serving |
| BuildKit cache after one build | 518.89 MB |

This proves the workload on this 4 GB host only. Peak host use was already
close to 1 GB despite the small fixture, so extrapolating this result to a
1 GB VPS would be unsafe. The 518.89 MB result motivated the explicit bounded
BuildKit GC policy added after this rehearsal; the drill itself predates that
policy and is not evidence of a completed GC sweep.

## Defects found and corrected

1. `deploy.sh` searched comments as well as assignments for placeholder text,
   so the complete production env template rejected itself. Placeholder
   validation now skips blank and comment lines; the full template is a
   regression case.
2. Compose defaulted BuildKit to four CPUs even on a two-CPU host, and Docker
   refused to create the container. `snaphostctl` now derives the smaller of
   four CPUs and the host count, and rejects an explicit impossible limit.
3. Production Compose created `snaphost_control`, while the host runtime asks
   Docker for `snaphost-net`. The control network now has the explicit name
   `snaphost-net`, guarded by a cross-file shell test.
4. A 7.4-minute build crossed the five-minute saga stale threshold. The
   sweeper queued it twice while the original job was still active; after a
   temporary runtime failure, the copies raced a deploy row that had already
   been marked failed and compensation hid the original error. The saga queue
   now admits at most one buffered or active job per deploy, and a backend
   start failure restores `building` through a fresh bounded context so the
   next sweep can actually retry it. Unit tests cover both invariants.

The build that exposed item 4 still completed its image successfully; it failed
only when item 3 prevented the site container joining the shared network. Its
568 memory samples showed a 910.2 MiB peak and no swap use.
