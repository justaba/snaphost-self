## Encrypted scheduled backup and actual database replacement

The test generated `/root/task7-evidence/restore-identity.txt` with
`age-keygen`, mode `0600`. Only its public recipient was put in
`/opt/snaphost/env/backup.env`, also `0600`. No remote storage was configured.
These root-shell commands illustrate that setup without exposing the identity:

```bash
umask 077
age-keygen -o /root/task7-evidence/restore-identity.txt
printf 'SNAPHOST_BACKUP_AGE_RECIPIENT=%s\n' \
  "$(age-keygen -y /root/task7-evidence/restore-identity.txt)" \
  > /opt/snaphost/env/backup.env
systemctl start snaphost-backup.service
```

The installed systemd service produced
`scheduled-20261005T115344Z.VBoXDr.sql.age`, 13653 bytes, mode `0600`, SHA-256:

```text
6d099f1ffa1b53b7a5ba6551217a3e925cf180258aa3ef94f7d33e84af70eb3c
```

`sha256sum -c` returned `OK`. Decrypting directly into a throwaway SQLite DB
returned `integrity_check=ok`, with 1 user, 2 projects and 2 deploys. The
following root-shell commands then replaced the actual installed database;
take a final recovery dump first on a live installation, as the
[restore runbook](../backups.md#restore) requires.

```bash
set -euo pipefail
umask 077
artifact=/opt/snaphost/backups/scheduled-20261005T115344Z.VBoXDr.sql.age
identity=/root/task7-evidence/restore-identity.txt
cd /opt/snaphost/backups
sha256sum -c "$artifact.sha256"
compose=(docker compose -p snaphost \
  --env-file /opt/snaphost/env/production.env \
  -f /opt/snaphost/infra/docker-compose.prod.yml)
app=$("${compose[@]}" ps -q snaphost)
volume=$(docker inspect --format '{{range .Mounts}}{{if eq .Destination "/var/snaphost/data"}}{{.Name}}{{end}}{{end}}' "$app")
image=$(docker inspect --format '{{.Config.Image}}' "$app")
"${compose[@]}" stop snaphost
age -d -i "$identity" "$artifact" | docker run --rm -i \
  --network none --user 1000:1000 -v "$volume:/data" \
  --entrypoint sqlite3 "$image" /data/restore.db
test "$(docker run --rm --network none --user 1000:1000 \
  -v "$volume:/data" --entrypoint sqlite3 "$image" \
  /data/restore.db 'pragma integrity_check;')" = ok
docker run --rm --network none --user 1000:1000 -v "$volume:/data" \
  --entrypoint sh "$image" -c \
  'chmod 600 /data/restore.db; rm -f /data/snaphost.db-wal /data/snaphost.db-shm; mv /data/restore.db /data/snaphost.db'
"${compose[@]}" start snaphost
curl --noproxy '*' --fail http://127.0.0.1:8080/health
```

After replacement the live DB again returned `integrity_check=ok`, contained
the expected rows, and had mode **0600**, UID/GID **1000:1000**. Health, login
and `/api/v1/auth/me` returned HTTP 200. Password rotation then succeeded:
the old bootstrap password returned HTTP 401, and the rotated password
authenticated with HTTP 200.

The verification DB was removed. No plaintext SQL artifact was created; the
service journal contained no private-key markers. The encrypted archive,
checksum and identity remained in protected VM paths. Keeping all of them
inside this VM is a restore drill, not protection against losing the machine.

## Linux CI cleanup regression

The [main workflow for `ba311579`](https://github.com/justaba/snaphost-self/actions/runs/37274111483)
failed at the Caddy integration step even
though all handshakes and certificate fingerprint checks passed. Its log ended
with `rm: cannot remove .../data/caddy: Permission denied`: Caddy had written
root-owned mode-0700 state in the non-root runner's temporary bind directory.

The suite now persists TLS state in a disposable Docker volume and removes
that volume during cleanup. The fixed script was copied to a throwaway test
checkout inside this VM and run using `sudo runuser -u boris -g docker -- bash
.../infra/tests/caddy_integration_test.sh` (UID 501, no root filesystem access).
It exited 0: control/project 200, alias B/A, detach 404, denied SNI, identical
SHA-256 certificate fingerprints across restart, no new order. Its temporary
containers, network, TLS volume and host directory were removed.

The final Node runner was also rerun after password rotation: cached build
`3fa82de1-4c03-4852-b06f-efe5d864334e` reached running in 3.0 seconds,
served HTML/JS with HTTP 200, and had zero OOM or restarts. The memory table
above records the earlier build, without this extra integration test running.
